# Protected package publication

The first release uses `1.0.0-rc.1` for all five packages. Issue #74 owns implementation and observed release evidence. Candidate preparation and registry publication are separate operations.

## Trust boundaries

`publish.yaml` builds, tests and creates a candidate using a read-only token on a GitHub-hosted runner without restored Actions caches. Pull requests, including approved fork PRs, can exercise that path. They cannot enter publishing: the publishing job requires manual opt-in, the canonical repository, `refs/heads/main`, and the protected `production` environment. NuGet's trusted publishing policy must name owner `knightfall`, repository `envoy-dotnet-control-plane`, workflow `publish.yaml`, environment `production`, and the authorized `Knightfall.Envoy.*` / `KnightFall.Envoy.*` patterns.

A fresh publishing runner downloads only the artifact ID produced by its own build job. It compares the handed-off manifest digest, complete file set, package identities, versions and source commits before requesting short-lived credentials. PR CI also downloads the uploaded artifact and verifies its manifest and complete evidence ZIP round trip, including hidden policy and lock files. The publisher does not restore/build candidate source or execute candidate binaries. Checkout is limited to trusted publishing scripts, SDK selection and release notes. The separate external-consumer jobs have package-read permission and execute the published libraries without publishing or OIDC rights.

The publishing job verifies the protected lightweight `v1.0.0-rc.1` tag points to the exact workflow commit and checks required main CI. Signing and publication use NuGet OIDC and `GITHUB_TOKEN`; no long-lived publishing key is added. Before publishing, the workflow verifies all three signed bundles with `gh`, constrains the signer/ref/commit and hosted runner, compares each complete subject/digest set, and compares each verified SPDX predicate with its corresponding expected SBOM. It checks any already-existing version in both registries against the candidate before starting package pushes; authentication or content conflicts stop the run. Duplicate skipping is permitted only for versions whose payloads matched during that check; an unexpected duplicate fails the push. The same package uploads go to both registries. The GitHub release remains draft until both fresh registry consumers pass. Registry publication is not an atomic multi-package transaction; partial failure must be investigated, and only failed jobs should be rerun to reuse the original verified candidate. Existing release assets are never overwritten.

## Workflow and repository controls

The release preflight requires all three CodeQL analysis jobs on the exact main commit: `Analyze (actions)`, `Analyze (csharp)` and `Analyze (go)`, each from GitHub Actions. Main branch protection separately requires GitHub's aggregate `CodeQL` PR check, which evaluates the pull request and is not emitted on main commits. Recorded main check data exercises the real PowerShell preflight in CI, including rejection of a failed analysis or wrong application.

All seven tracked workflows are onboarded to the machine-generated `.github/workflows/actions.lock`, including transitive action dependencies and repository identities. Regenerate with the checksummed `gh-actions-lock` version in `.github/security/tools.json`; never edit the lock manually. `workflows verify --cache <external-tool-cache>` runs actionlint, zizmor and online lock provenance verification. The lock verification command is read-only. Container images and reusable workflow calls are outside native action-lock coverage; existing Envoy images retain their independent digest lock.

The sole zizmor exception is the isolated Dorny `workflow_run` reporter recommended for fork PRs. It checks the producing repository/workflow path, reads report artifacts through the pinned parser and writes checks. It never checks out parent code, runs shell commands, restores caches or executes artifacts. Changes to that boundary require owner review.

Reviewable settings live in `.github/security/`: main changes require PRs, current required checks and resolved conversations without a CI bypass; code ownership applies to workflows, locks, package/build/source generation and release inputs. Only the repository administrator can bypass the separate human-review rule through a PR because this repository has one maintainer. This is not a two-person review guarantee. The existing Copilot ruleset is preserved. Release tag creation is administrator-only; update/deletion of `v*` tags is prohibited. `production` permits only main deployments, requires `knightfall` review and forbids administrative bypass. Self-review is allowed solely so the single maintainer can approve their own manually initiated release.

Fork workflows retain read-only tokens; workflows from external contributors require maintainer approval before running. Actions are restricted to GitHub-owned actions and the explicitly needed NuGet/Dorny actions; full pin/lock requirements remain enabled. NuGet restore audits all transitive dependencies at moderate severity or higher, with warnings-as-errors. Dependabot proposes dependency updates; none are automatically merged. CODEOWNERS and environment protections do not remove the repository owner's ultimate administrative control.

## SBOMs and verification links

The checksum-pinned Microsoft SBOM Tool generates and validates an SPDX 2.2 build SBOM from the restored repository and release files. Verification also requires every direct/transitive dependency in the five runtime package locks to appear with its exact version. It is a build inventory, including test/tool dependencies, rather than a per-package runtime-only dependency claim. A companion SPDX source document records original schema/reference archives, the source-built evaluator and migration tool, with immutable revisions and archive hashes. The tool links that source document as an external reference. Exact adaptations, licenses and generated fingerprints remain in the release evidence. The SBOM tool is reused; no dependency scanner is reimplemented.

Every package contains `security/provenance.json` and a README pointing to its versioned GitHub release and attestations. This metadata is a verification locator. The signed attestations are generated after the final package bytes exist; embedding their IDs in those same bytes would invalidate the attestation digest. GitHub release assets include the signed bundles, both SBOMs, packages/symbols and a complete evidence archive.

NuGet repository signing adds `.signature.p7s` and changes archive bytes. Verify the original upload package from the GitHub release with `gh attestation verify`, constraining the signer workflow, source ref and source digest. Verify the downloaded NuGet package with `dotnet nuget verify --all`. `compare-packages.py` compares every other ZIP entry with the attested artifact; altered content or duplicate entries fail. The external-consumer jobs perform those checks and run a fresh .NET consumer against each registry with source mapping and an empty package cache. The same consumer source and preparation script also run against the local candidate in read-only PR CI before publication, so API or compilation errors cannot first appear after a push.

## Release procedure

These steps describe the completed first release. The current workflows and recovery constants are pinned to `1.0.0-rc.1`; prepare and review version-specific updates before a future release. Do not reuse the recovery workflow to publish another version.

1. Finish the single publishing PR, requested Terra high review, automatic Codex PR review and exact-head CI. Apply and re-read the tracked repository/environment protections; do not silently replace unrelated settings.
2. On verified merged main, create the protected lightweight release tag at that exact commit. Existing tags are never moved. Confirm the NuGet trusted publisher policy and actual package ownership.
3. Dispatch `publish.yaml` on main with `publish: true`. Review the build/SBOM artifacts and approve its pending `production` deployment in GitHub. A dry dispatch defaults to `publish: false` and produces no registry writes or signing credentials.
4. Verify both registry consumers, all three attestation classes and release assets; publish the GitHub announcement only after consumption passes. Record immutable run, commit, package and attestation links in issue #74.

Main packages and symbols are pushed separately because NuGet skips automatic symbol upload after a duplicate main package. A loopback V3 registry check exercises the installed SDK's package/symbol endpoints and duplicate behavior in PR CI. It uses dummy credentials and performs no external publication; real NuGet symbol indexing remains a release-service check.

Configured controls are not observed deployment proof. This document must distinguish locally tested candidate preparation, GitHub CI, applied settings, production approval and actual external publication.

## Recovering verification of the published candidate

The first production run [42336411459](https://github.com/knightfall/envoy-dotnet-control-plane/actions/runs/42336411459) successfully attested and pushed all five packages and their NuGet symbols. Its external checks failed afterward: the GitHub consumer omitted the required validator `failFast` argument, while NuGet had not finished indexing within the retry window. A fresh local NuGet check then exposed duplicate names for the same feed URL, which caused NuGet to omit the dependency mapping. The corrected NuGet configuration defines that feed once with a wildcard mapping; candidate and GitHub consumers retain separate sources and own-package mapping. Those failures do not justify rebuilding an already published version.

The manual `verify-published.yaml` workflow is scoped to that original run and artifact ID, its protected source commit and its exact manifest SHA-256. Run it on main after merging the verification fix. Both read-only consumer jobs verify the protected tag, every candidate file and the signed manifest's original publishing workflow, source ref, source digest and hosted runner before executing packages. After both pass, the separate announcement job downloads the existing draft assets, compares all packages, symbols, SBOMs, manifest and complete evidence ZIP, then verifies all three saved signed bundles and their complete subjects/data before making the draft public. GitHub exposes draft releases only to users with push access; the first recovery run failed closed when its read-only consumers attempted to read the draft. Draft evidence verification therefore runs in the announcement job, which already needs contents-write permission and never executes candidate libraries. Package-executing jobs retain read-only tokens. The workflow has no OIDC or package-write permission and cannot sign, rebuild or republish packages. It uses the original Actions artifact within its 30-day retention period; after expiration it fails rather than substituting another build.

The immutable package source/tag remains `000438a9c4d0bc0b58a5ec7bc55af10f5f9c0ccd`; the verification fix has a later commit. The successful [recovery run 42340393784](https://github.com/knightfall/envoy-dotnet-control-plane/actions/runs/42340393784) verified both registries and announced the release; [issue #74](https://github.com/knightfall/envoy-dotnet-control-plane/issues/74) records both identities and the evidence. Ordinary publication retries still use failed-job reruns of the original run. The recovery workflow specifically handles verification code fixed after successful publication.
