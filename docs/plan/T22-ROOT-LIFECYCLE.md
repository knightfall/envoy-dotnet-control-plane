# T22 — Root concurrency, callbacks and cleanup

Completes the remaining root-library lifecycle scope in [issue #28](https://github.com/knightfall/envoy-dotnet-control-plane/issues/28), building on [preview evidence](T22-PREVIEW-LIFECYCLE.md). The implementation adds seven cases and extends one timer case. Production APIs, coordination policies, dependencies, schemas, generated fingerprints and source pins are unchanged.

## Added boundaries

- `DeltaStreamTests.ClosedResponseWriter_FailsUnavailableAndReleasesEveryOwnedResource` registers two types, closes the custom producer's response writer, and checks the Unavailable error, both registration disposals, input disposal, terminal stream task and one close callback.
- `DeltaStreamTests.CleanupFailures_RetainPrimaryErrorAndAttemptEveryOwnedReleaseOnce` rejects a request after two watches exist, then makes both asynchronous watch releases, input disposal and close fail. It checks that the original request failure is retained, every failure is reported and every owned release is attempted once. Synchronous disposal must never substitute for the asynchronous contract. This covers Delta's separate cleanup implementation; the SotW cleanup test alone cannot establish it.
- `ActiveCallbackShutdownTests.DeltaApplicationStopping_CancelsActiveCallbackAndReleasesBothTypes` covers active request and response callbacks. Each reenters publication on the same cache after registering two types, then waits on an unreleased gate. Direct ApplicationStopping cancels the callback and releases both watches before ApplicationStopped or StopAsync, without client cancellation. The shared cache remains caller-owned.
- `ActiveCallbackShutdownTests.FetchApplicationStopping_CancelsActiveHookBeforeStopDeadline` covers request and response hooks over actual unary HTTP/2. The response-hook contract has no context argument, so application code captures the original request context token. Direct ApplicationStopping cancels that token, ends the hook and RPC before a stop deadline, and creates no stream watch/status. This preserves ordinary framework error handling rather than adding a new transport status policy.
- `HeartbeatTests.BlockedHeartbeat_StopRetainsWatchAndAllowsNormalPublication` now tracks the ITimer through the existing injected TimeProvider. The blocked loop owns one timer; awaiting shutdown leaves zero. Existing assertions prove that the pending watch survives timer shutdown and later normal publication succeeds. The test uses Microsoft's existing fake clock and no new runtime seam or package.

## Bounded Delta transport repetition

`DeltaStressTests.RepeatedAdsRounds_UpdateRemoveAndReleasePendingWatchesWithRecordedMemory` uses seed 43623, sixteen rounds, four nodes and Cluster/Route ADS types. Plans are computed before workers run. Every round includes immediate and deferred publication and normal and canceled stream endings.

The test checks 64 actual HTTP/2 streams and 256 responses. Each type starts with resources a/b, then receives only new resource c and removal a; unchanged b is suppressed. Type URLs, system/resource versions, serialized payloads and nonce uniqueness are checked. ACKs use the received per-type nonces. Three registration barriers expose the initial, initial-ACK and replacement-ACK watch states; each stream ends while its final watches are pending.

All worker tasks terminate within failure bounds. Every round checks exact request/response/open/close counts, unique stream IDs and zero remaining watches. The test explicitly clears its own snapshots and status and drains observer queues. Stream closure does not promise to delete caller-owned cache status. The fixed seed records 33 normal endings and 31 cancellations.

The report records seed, counts, elapsed duration, platform/runtime/architecture and sixteen process-wide managed-memory/working-set/watch samples. These diagnostic samples can include other tests and GC activity; they do not establish a memory budget, throughput threshold or fairness guarantee. Timeouts fail the test. The repository verifier retains delta-stress.json alongside the two existing SotW reports under Protocol's obj/upstream/results/lifecycle, which existing CI uploads. This correctness run does not enable the manual gRPC performance workflow on PRs.
